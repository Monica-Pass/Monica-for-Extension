# KeePass password project member removal

Status: planning, encrypted intents, isolated complete-file preparation and atomic working-copy/receipt persistence verified; user workflow remains unfinished.

The extension already groups native KDBX password projects, but the member-removal editor is still limited to local/MDBX sources. The intended result is removal of selected passwords or credential groups while retaining all other passwords, native identities, history, project content and attachments, with durable restart/conflict recovery.

`planKeePassProjectRemoval` now validates the complete current active project against the original editor snapshot, including archived members. It detects content changes even when timestamps are unchanged, added/missing members, duplicate identities, switched sources, reused new-row IDs, native UUID changes and changed password IDs. Other databases and old trash are excluded by scope. Shared project/account edits are reconciled before choosing the new content owner. The returned plan preserves exact metadata strings and specifies owner transfer without modifying input data.

45 targeted tests pass across the planner, shared removal/reconciliation and KeePass provider. One test applies a non-owner password removal through the real provider to an encrypted KDBX and reopens it, checking remaining native UUIDs/password IDs/secrets and the removed entry's trash state. This is file-level validation, not Edge UI, remote-server, Android application or owner-attachment-transfer acceptance. Both TypeScript configurations pass.

The native attachment handoff now prevalidates source/destination ownership in the same open database, rejects same-name different bytes or protection, and rechecks exact attachment contents and identities immediately before changing the target. It preserves destination-only attachments and its pre-transfer history, and keeps the source binaries for recycle-bin restore. Temporary comparison bytes are wiped on apply/dispose. Encrypted-file tests cover protected binaries, identical-file deduplication, stale same-size replacement, missing/extra files, detached/trashed entries, replay after reopening and exact source restore. A real project plan is also applied with shared-content edits, owner handoff and removal in one saved KDBX revision, preserving all password IDs and secrets. This is a file primitive, not the production sync transaction.

`SecureVaultService.stageKeePassProjectRemoval` now persists the full draft/originals and source snapshot in one encrypted local intent without changing live items or queuing independent deletions. Same-operation retries return the saved intent after restart, including a committed-write/lost-acknowledgement case. Different drafts, source replacement, stale originals and overlapping intents are rejected. Cancellation retains a terminal receipt; retry cannot reopen it. The internal methods have no runtime/UI route yet. File-level revision and attachment proofs are still required before resuming the staged intent; no automatic execution or completed-removal receipt is claimed.

76 targeted tests across seven files pass; both TypeScript configurations pass. The initial attachment test typecheck failed on Uint8Array/ArrayBuffer argument types and was repaired; its original log remains retained.

`KeePassProvider.prepareProjectRemovalFile` now builds the complete replacement in an isolated KDBX session. The exact input SHA-256 and current native project membership/content are validated before edits; retained writes, unsaved member creation, attachment handoff and removals all land in the returned encrypted file. A failure during field writing or serialization discards the isolated copy without changing the live provider or supplied bytes. Replacing all old members with a new retained password, including attachment transfer, is covered.

`KeePassRemoteSessionService.persistProjectRemoval` now commits those exact output bytes and an encrypted `project-remove` receipt together using the working-copy store revision CAS. The request binds the expected input file hash and source identity. Repeated requests recover the original receipt after response loss/restart, while a different source or draft is rejected. The original remote baseline remains intact. Tests inject before-commit failure, committed-write response loss and a revision race; no partial file or duplicate deletion survives. The method intentionally does not publish, reload the live provider or adopt cached items: those steps still require the coordinator.

Latest validation: 104 tests across eleven files pass, including existing working-copy/receipt/session tests; both TypeScript configurations pass. Initial tests selected the removed row instead of a retained row for a write-failure fixture; that fixture was corrected. Typecheck also caught unsupported Array.at and an inferred optional binary-map entry; both were repaired with failure logs retained.

Encrypted intents now support `writing` and `completed` phases. `beginKeePassProjectRemoval` persists the exact input file hash before any native write and rejects pending project mutations, stale originals or replaced sources. Once writing begins, direct cancellation is refused because a native file commit may already exist. `completeKeePassProjectRemoval` checks the shared request digest, source/file binding, complete result membership, password values, native identities and credential metadata, then adopts all results and the completed intent in one encrypted commit. A later local edit or queued mutation is retained as a recoverable conflict. A completed receipt replay never reinstalls an old item snapshot.

Real KDBX/working-copy receipts were exercised through the actual encrypted vault service: failed local adoption, acknowledgement loss after adoption, fresh-service unlock, and edits after completion all pass. A wrong receipt digest and concurrent edit reject without changing the vault. Latest regression: 107 tests across eleven files and both TypeScript configurations pass (`raw/keepass-removal-adoption-{regression,check}.log`).

`KeePassProjectRemovalWorkflow` now sequences stage/begin/native receipt lookup/persistence/local completion under `ProviderOperationQueue`, with manager-safe status and serialized cancellation. It reads an existing native receipt before attempting another write, rechecks source binding after waiting, and rejects later project edits before a first native commit. A real encrypted-vault/KDBX integration test restarts the workflow after native response loss and completes without another file revision. A blocked-queue source replacement and a pre-native local edit both prevent writing. Latest validation: 109 tests across eleven files and both TypeScript configurations pass (`raw/keepass-removal-workflow-{regression,check}.log`).

The workflow is now instantiated in `background/index.ts` with lifecycle hooks for `runKeePassMutationExclusive`, live-session persistence before hash capture, and session invalidation after every attempted native file commit (including lost acknowledgement). Ordinary provider sync recovers pending intents before entering KeePass synchronization; `ensureKeePassSession` then reloads the durable file because the old session was invalidated. Remote attachment/group/history mutations reject while an intent remains pending. This preserves the existing outer `providerOperations` / inner KeePass mutation queue ordering without recursively acquiring the outer queue.

Lifecycle tests add an attachment only to the live session before removal, verify it reaches the durable file and both project owners, inject native response loss, recover, reload, run ordinary provider sync and save again. The removed member stays in trash and neither original nor newly added attachment is lost. Latest validation: 111 tests across eleven files, both TypeScript configurations and production extension build pass (`raw/keepass-removal-lifecycle-{regression,check,build}.log`). Build asset verification passes for all three extension pages; existing large-chunk warnings remain.

Manager-only runtime/client APIs now expose source-token capture, explicit-confirmation removal, pending status, resume and cancel. The editor token is an HMAC over source identity/credentials using the current unlocked session as key; source secrets never leave the background, and password guessing against a plain public digest is avoided. Saving rechecks the token while holding both queues and stages the exact verified source snapshot. Path, credential or unlock-session changes invalidate the old token; sync bookkeeping does not. Successful local adoption explicitly schedules the source for automatic publication even though no per-entry mutation remains queued.
