## Android changes still required

2026-10-06 user clarification supersedes the earlier proposed counter fix: Android intentionally always signs with zero to avoid counter divergence across offline synchronized copies. Retain that policy; do not introduce increment/reservation or rewrite existing credentials in this repair batch. The recorded count43→0 response is a compatibility failure under this test RP's strict positive-history policy, not evidence that always-zero credentials need incrementing. Some RPs may reject such a transition, but local increments also cannot solve ordering across offline copies. Investigate this boundary separately before proposing any policy change; keep the original response and strict test result intact.

Authenticator backup flags must be derived from the stored credential's creation metadata, not hard-coded29. `MonicaCredentialProviderService` must not fall back to discoverable records after a nonempty allow-list has no match; the authentication activity should independently require the selected ID to be allowed. Its Cancel action should return cancellation rather than request a different authentication method.

These are reproducible Android-side gaps under the current read-only Android scope. Browser-origin validation, real OneDrive login/SPA registration and system-CM use, and the wider rich-password parity matrix remain open. The later three-backend report above supplies the added KDBX/WebDAV/Bitwarden system evidence without resolving these failures.
