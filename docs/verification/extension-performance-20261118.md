## 初始资源与建议

实测德语首次使用管理页请求约2.94MiB本地资源，弹窗约1.78MiB，包括409,781字节德语词库、字体、图片及共享模块；不是互联网下载量或gzip值。管理页主JS约800kB、共享client约425kB、Material controls约280kB、URL rules约261kB。

1. **优先减少同步/写入的整库成本。** 无本地待写/无恢复操作的revision检查避免复制，复用未变条目及来源索引，再评估逐记录持久化。保留锁代、账号绑定、冲突、加密回执和事务语义。
2. **减少管理页全量快照和派生。** App.vue的refreshItems仍获取完整条目快照，前台分页只限制可见行；评估摘要分页、按修订刷新和选中详情读取。当前网站匹配也应评估后台有界返回。
3. **继续拆分静态依赖。** App.vue→LoginEditorFields→PasswordContentEditor→VaultItemEditor存在静态导入，首次使用页已请求约97kB编辑器chunk；顶层defineAsyncComponent尚不能证明完全按需加载。Popup共享client/Material组件/URL规则也值得按实际资源图拆分。
4. **独立测量密钥复用和复杂网页。** 不降低KDF或加密强度；真实跨域iframe、常驻大页面、附件库、复杂密码项目组、长期运行均未覆盖。

## Android 对照与原生文件读写边界（后续只读核对）

未做同服务器、同数据集、同设备条件的 Android/扩展测速，不能给出两者的速度倍率。核对当前普通 Android 源码：`BitwardenRepository` 的常规同步调用 `BitwardenSyncService.fullSync`，下载 `/sync` 完整响应；前台通知触发普通同步。`CipherSyncProcessor` 对满足完整未变条件的记录跳过正文解密/更新，变化记录以 Room 事务更新。`BitwardenCipherSourceStore.accept` 则在逐 Cipher 接收事务中加密保存原始来源文档，因此不能称 Android 无变化同步完全零加密或零写入。

扩展正常单 Cipher 通知可以只拉取该 Cipher，网络增量比上述 Android 常规全同步更细；但协调器先 `readState` 并复制条目，最终保存仍是主库完整加密信封。Android 的本地持久化主要按记录进行，没有扩展这种每次变化重写主库完整 JSON 信封的路径。这个架构差异说明优化方向，不证明 Android 整体更快。

KDBX 扩展使用 kdbxweb 操作真实原生 KDBX 对象，保留原生字段、附件和历史；本地修改保存在加密工作副本，最初选择的桌面文件不会自动覆盖，需导出保存。远端 KDBX 在变更后重新编码完整文件，按 ETag 条件上传。KDBX 的原生格式读写不是逐记录原地磁盘更新。

MDBX2 新库默认使用内置 Rust/WASM 引擎，按对象/事务操作原生数据库。浏览器路径为 MEMFS 工作文件加 IndexedDB 64 KiB 块持久化，提交只保存变化块及目录元数据；不是把所有记录转成 Monica JSON 后每次整体加密保存，也不是自动覆盖最初选中的桌面 MDBX 文件。已有 Native Host 来源沿用其原后端，助手管理的工作副本与浏览器副本不能混称。界面投影、同步和控制元数据仍有自己的读取/复制成本，本次没有对 KDBX/MDBX 大库性能做专项计时。

上述后续核对只读源码，没有修改 Android、操作设备或用户数据库。性能优先级仍是扩展 Bitwarden 无变化路径的全库复制、单变化的主库完整写入，以及批次密钥导入复用；逐记录加密存储需要独立迁移和恢复设计，不能通过降低加密/KDF或跳过持久回执来优化。
