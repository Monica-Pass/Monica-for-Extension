Date: 2026-11-04 (Asia/Shanghai). Baseline: `f027c0f`. Extension version remains 1.0.103; final source build: `63c00b1b2fb3a3aa8b3e`. No commit, push, tag or publication performed.

## Implemented flow

- Settings now show version, build ID and extension ID. A successful check offers a direct ZIP link only for a strictly higher official stable version and exactly one matching extension asset. Same-version previews cannot be replaced through that direct download action by older stable code.
- The asset must have the exact expected versioned ZIP name and official repository/tag URL, uploaded state and a positive integer size no greater than 128 MiB. Missing or untrusted assets retain the release-page fallback. GitHub response text is not rendered as HTML. Existing request limits, credential omission, timeout and owner cancellation remain.
- Chromium users get instructions to extract the ZIP into a temporary directory, replace the original loaded directory without an extra nesting level, save edits and reload. The management shortcut opens the current extension's browser page. Reload requires an explicit confirmation about closing Monica pages and losing unsaved edits.
- This is a guided manual update. It does not automatically replace filesystem contents, uninstall the extension, clear storage, migrate credentials or sign in to Bitwarden. Firefox retains the release-page flow and does not receive the Chromium ZIP/install guide.
- All 13 new strings are translated into English, German, Spanish, Japanese, Korean, Russian and Vietnamese in addition to Chinese. Long words and buttons wrap within the update panel at large font sizes.
- README now explains the official manifest key and correct original-directory update procedure; the unreleased bilingual changelog preserves the earlier TOTP entry.

## Diagnosis

1. **Old background code after file replacement was reproduced.** An isolated installed Edge profile first loaded the actual stable 1.0.103 package (build `14ab010da0d35b85e20e`). With its worker still alive, the test copied current build files over that directory. The newly opened manager still received the old build identity. The existing mismatch guard displayed its reload action; using it activated the current build. No new runtime mismatch logic was needed.
2. **Same-directory replacement preserved data.** The SHA-256 of the serialized primary encrypted IndexedDB envelope matched before replacement and after runtime reload. Unlocking with the original Monica master password and making an authenticated encrypted export recovered the exact original synthetic items and Bitwarden provider configuration, including synthetic token and device fields.
3. **Changing directory alone did not create a new identity.** After closing the test browser without uninstalling, the test loaded a second directory through the same isolated browser profile. The extension ID remained `lebnfedmijifofonogjdphpojihgohmc`; fetching a marker present only in the second directory proved it was actually loaded. The encrypted primary envelope still matched, and the original master password unlocked the same items.
4. The official tags inspected (`v0.1.48`, `v1.0.101`, `v1.0.102`, `v1.0.103`) contain the fixed manifest key introduced by `a16770d`. The former README claim that unpacked identity always depends on directory was therefore stale. A custom package without that key, another browser profile, uninstalling or clearing extension storage remain distinct conditions; none is established by the report.

The Bitwarden fixture is disabled and contains synthetic credentials, so the test proves local configuration retention, **not** continued validity of a real server session or absence of server-requested authentication. Different extraction layouts, interrupted copies, file locks/permissions, actual user databases, other browsers and Firefox installation were not tested. The relocation test uses command-line extension loading, not a human-operated folder picker.
