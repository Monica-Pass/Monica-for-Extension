# 浏览器扩展性能第一批优化（2026-11-12）

范围：扩展1.0.104的下一版改动，未升版、提交、推送或发布。用户要求不影响Android主会话；本轮只修改monica-extension，未执行Android构建、模拟器、ADB操作或调整既有进程。重型验证串行、BelowNormal优先级、两个逻辑CPU、单测试worker；启动时空闲内存不足3GiB则延后。

## 实现

- 普通Bitwarden同步诊断与同步结果采用同一次加密提交。仍经过账号绑定、冲突、同步快照和加密写入检查，诊断沿用脱敏及最多100条。结果入库失败或入库前取消不留下成功记录。远端写入prepared/attempted/committed回执仍按原顺序分别持久化，失败诊断保留独立路径。诊断duration记录到入库准备，不包含其所在事务提交。
- 分批同步的剩余项目提示在准备提交前生成，使持久化诊断的警告数与返回结果一致；保持项目整体分批和重启续传规则。
- Popup先发布当前网站登录摘要，Passkey、卡包和全部登录摘要随后补齐。每次结果发布检查刷新代和锁定状态，切换目标/重新初始化/失败后撤销迟到发布；实际填写仍在后台检查documentId、origin和授权。没有减少加密强度或放宽免解锁授权。
- 空卡包类型集合不复制全库。显式密码复制使用getItem，保留非登录、回收站和归档拒绝规则。
- 20页以内保留原页码下拉；更多页时在同一M3E表单组件内使用数字输入，Enter或提交change跳转，保留上一页/下一页、范围钳制和空值恢复。总页数不再线性增加m3e-option数量。

## 同条件性能对照

两侧都使用BelowNormal、两个逻辑CPU、Node线程池2、单进程串行测量。其他会话继续运行，没有隔离整台机器负载，因此小样本耗时只表示本机趋势。旧版编译探针在修改前保留并经SHA256核对；两侧均包括正常同步诊断，避免将旧版两个独立计时相加。

### Bitwarden生产链路合成测量

单位毫秒；冷同步每侧1次，单条增量和未变化检查每侧3次取中位数。

| 条目数 | 操作 | 优化前 | 优化后 | 每次完整信封写入次数：前→后 |
| ---: | --- | ---: | ---: | ---: |
| 100 | 冷缓存完整同步 | 315.1 | 233.5 | 2→1 |
| 100 | 单条Cipher变更 | 61.0 | 35.2 | 2→1 |
| 100 | revision未变化 | 7.4 | 5.5 | 0→0 |
| 1,000 | 冷缓存完整同步 | 1,898.8 | 1,074.7 | 2→1 |
| 1,000 | 单条Cipher变更 | 548.1 | 355.2 | 2→1 |
| 1,000 | revision未变化 | 50.5 | 66.4 | 0→0 |
| 5,000 | 冷缓存完整同步 | 6,149.9 | 4,952.4 | 2→1 |
| 5,000 | 单条Cipher变更 | 2,512.3 | 1,633.9 | 2→1 |
| 5,000 | revision未变化 | 228.9 | 268.8 | 0→0 |

5,000条单条增量减少约35%耗时，累计交给存储接口的信封JSON从22,804,432降到11,402,378字节（约21.75→10.87MiB）。这是两次/一次完整信封的字节总数，包含Base64与元数据，不是网络流量或实际磁盘写入量。两侧该操作均只GET一个Cipher；未变化检查只GET revision、不写入。这些结构性断言全部通过。

未变化检查在1,000/5,000条样本中反而更慢，不能宣称本批改善了这条路径；代码仍做全库上下文复制，且测试未隔离其他负载。独立诊断写入、前台读取排队以及逐条本地修改仍有整库成本。新旧比较脚本：`run-sync-comparison.mjs`，结果：`sync-comparison.json`、`sync-before.json`、`sync-after.json`。

## 范围与后续

本轮不修改整库存储格式，因此单条同步仍需一次完整加密写入。没有实现逐记录存储、全库摘要的后台分页、Bitwarden CryptoKey缓存或大范围组件拆包；这些仍是后续优化点。

后续按优先级推进：

1. **高优先级：后台摘要分页与按修订刷新。** 当前前台分页只限制可见行数，全库消息传输、搜索预处理及刷新仍随数据量增长。先减少传输及复制，再考虑更复杂的搜索索引；列表摘要不携带密码/密钥。
2. **高优先级：Bitwarden本地增量。** 现有网络增量有效，但未变化检查和单Cipher更新仍复制/遍历完整本地上下文。区分无本地待写/无恢复操作的轻量revision检查，复用未变条目与来源索引，保留并发本地修改、账号/锁代及异常空库保护。
3. **中优先级：冷同步密钥复用、按需加载和网页扫描。** 先测量单批CryptoKey复用及小规模有界并发；管理页静态大模块延迟加载；复杂Shadow DOM/多frame页面扫描需要独立trace确认。目前只确认源码开销，未证明这些就是反馈用户的具体慢点。
4. **独立架构工作：逐记录加密存储或增量日志。** 需要兼容迁移、可验证恢复点、崩溃一致性与回执恢复设计，不能用取消写队列、降低KDF或延迟持久化恢复回执来换速度。

测试使用本机合成数据和隔离Edge配置，无用户库、真实云账号、Firefox或物理设备验收；未与官方Bitwarden扩展做同机同库横向比较，原用户反馈尚无明确复现条件。Node对照使用真实生产provider/coordinator/vault及WebCrypto、进程内HTTP和MemoryVaultStorage，不包含网络、IndexedDB磁盘延迟、KDF或复杂附件。浏览器探针测试URL共享example.test根域，全部登录匹配属于压力场景，不代表一般网站。V8堆和CDP节点（含Shadow/分离节点）不等于浏览器总内存或泄漏数量。没有运行全仓全部E2E、完整发布检查或新建发布包；版本仍1.0.104，未提交/推送/发布。
